## 第 0 站 · 先建立"这是什么"的直觉

**做什么**
1. 用无模型模式在 Web 上跑一个任务（零成本），看时间线里事件是怎么一条条出来的

## 第 1 站 · 数据模型：`graph/state.py`（88 行）

**为什么先读它**：状态是"在图上流动的东西"。先知道**流动什么**，再看**怎么流**。

**重点看三件事**
1. `Annotated[list[AnyMessage], add_messages]` —— `messages` 为什么需要 reducer（多个节点都往里加）
2. `Annotated[Budget, add_budget]` —— `budget` 为什么是**累加**而不是覆盖
3. 其余通道（`status` / `summary` / `attempts`）为什么不需要 reducer（last-value-wins）

**顺带记住两个类型别名**（后面每站都会看到）
- `NodeFn = Callable[[AgentState], dict[str, Any]]` —— **节点只返回增量**，不返回整个 state
- `RouteFn = Callable[[AgentState], str]` —— 条件边就是一个"读 state 返回下一个节点名"的函数

**自检**
- 为什么 `messages` 用 `add_messages`，而 `status` 不用？
- 一个节点如果返回 `{"status": "done"}`，`messages` 会怎样？

## 第 2 站 · 拓扑：`graph/builder.py`（109 行）

**这是全项目信息密度最高的文件** —— 一张图的全部接线都在这里。

**重点看**
1. 五个节点是怎么 `add_node` 的
2. `add_edge` 串起来的直线部分（intake → plan → act）
3. **条件边**：`reflect` 之后怎么决定回到 `act` 还是去 `finalize` —— 这是全项目的"大脑分叉"
4. `build_default_graph` 怎么把真实依赖（模型 / 工具 / 工作区）装进去，而 `build_graph` 只收注入的依赖

**为什么这个设计重要**：`build_graph` 的**依赖注入接缝**（planner / judge / agent / project_doc 全部外注入）
换来了三件事：零 API 跑通全图、无模型模式、以及后续做消融实验的前提。**面试问"你的可扩展性在哪"，答案在这一站，不在框架。**

**自检**
- 手画出这张图（五个节点 + 条件边）
- "验收没通过"时走哪条边？连走几次之后会发生什么？

## 第 3 站 · 四个节点：`graph/nodes/`（276 行）

按执行顺序读：`intake.py`(40) → `plan.py`(57) → `act.py`(42) → `reflect.py`(111)，`finalize.py`(26) 最后看。

**每一站只问一个问题**：这个节点**读** state 的什么，**写**回什么？

**两个必须看懂的点**
1. **`act.py` 的消息处理**：子图交回的是「输入 + 本轮新增」，而 act **全量**交回主图。
   为什么不会重复？因为 `messages` 挂的合并函数会给缺 id 的消息补 id，再按 id 合并 ——
   输入那部分被原样替换回去，所以不会变成两份。
   **这里原本有一段按长度切片的代码**，注释声称"不切片就会重复累积、放大 token"。
   实测推翻了该因果（两种写法的消息条数完全一致），切片不但多余，还隐含
   "输入必然是返回结果的前缀"这一位置假设，已删除。**这条注释的错误比它难看更值得记住：
   代码说错了机制，照着学的人就会学错。**
   完整过程（含三轮实验）见 `注释审计_承重断言.md`。
2. **`reflect.py` 的四个出口**：通过验收 / 还能重试 / 达到步数上限 / 超过重试上限 ——
   每一个出口对应的 `status` 和 `summary` 是什么。

**自检**
- `act` 全量交回主图，为什么不会造成消息重复？靠的是哪个机制？
- 达到 `max_steps` 时，任务最终是什么状态？用户看到什么？
- 重试时，上一轮的验收意见是怎么传给下一轮 `act` 的？

## 第 4 站 · 工具层：`tools/fs.py`（325）+ `workspace.py`（70）

**这层是"给模型的手"**，也是本项目最值钱的设计。

**三个设计点（都值得能讲出来）**
1. **路径边界**：每个工具第一步都过 `Workspace.resolve()`，越界直接拒绝。
   —— 为什么安全边界不能只做在 prompt 里（模型可以被诱导），必须做在工具实现里。
2. **错误即文本**：工具内部捕获异常，返回 `[tool_error] ...` 让模型**自己纠错**，而不是抛出去中断整张图。
   —— 这是 Agent 工具与普通函数的本质区别：**错误是给模型的输入，不是给程序的异常**。
3. **诚实截断契约**：`glob` / `list_dir` / `search` 一律报告 `truncated` + 真实总数。
   —— 背景是踩过的坑：静默截断会让模型**自信地给出错误的文件总数**。

**自检**
- 如果一个工具改成抛异常，会发生什么？图会中断在哪里？
- `search` 返回的 JSON 里，为什么要有 `files_scanned` 和 `files_skipped_binary`？
- 现在**没有**的东西是什么？（提示：`write`/`edit` 没有任何权限拦截 —— 见 `known_issues` 开放项 1）

## 第 5 站 · 从图到产品：`serve/`

按**数据流向**读，顺序很重要：

| 顺序 | 文件 | 行数 | 角色 |
|---|---|---|---|
| 1 | `runner.py` | 106 | **执行**：把图跑起来，累积状态，发事件 |
| 2 | `events.py` | 175 | **翻译**：把 LangGraph 的原始输出 → 前端事件（**纯函数**） |
| 3 | `bus.py` | 98 | **分发**：事件总线，支持 `Last-Event-ID` 续传 |
| 4 | `app.py` | 281 | **入口**：HTTP 路由、SSE 端点、目录浏览、模型列表 |

**重点看**
- 为什么 `events.translate` 要写成**纯函数**（可离线测、可回放、不依赖运行时）
- 一次 `tool.started` 事件从哪产生、经过几个环节到浏览器
- `app.py` 里的 `API_VERSION` 握手 —— 为什么需要它（**踩过的坑**：静态托管每次读盘，旧进程会把新前端发出去）

**自检**
- 把 `events.translate` 单独拿出来测，需要起服务吗？为什么不需要？
- 服务重启后，前端为什么还能续传事件？靠什么？

## 面试自检：读完应该能脱口而出的 10 个问题

1. 这个 Agent 是"什么样的 Agent"？主图和子图各管什么？
2. 模型是怎么知道有哪些工具的？**谁来决定调用哪个工具**？
3. 为什么 `docstring` 这么重要？举一个它影响模型行为的实证。
4. 状态里的 `messages` 和 `budget` 为什么需要不同的 reducer？
5. `act` 全量把子图消息交回主图，为什么不会重复？靠什么机制保证？
6. 条件边的判定逻辑在哪？"验收不通过"的完整路径是什么？
7. 工具为什么把异常转成 `[tool_error]` 文本？
8. "诚实截断契约"是什么？不做的时候踩过什么坑？
9. 这个项目**没有**什么？（记忆、权限、沙箱、持久化 —— 能说清各自的后果）
10. 如果要加"跨会话记忆"，你会从哪里下手、需要动哪些文件？

## 阅读时怎么用我

三种模式，你挑：

| 模式 | 怎么配合 |
|---|---|
| **你读，我考** | 你读完一站，把自检问题答给我，我指出偏差并追问 —— 最接近面试的真实压力 |
| **我讲，你打断** | 我按站讲解（重决策依据与踩过的坑，轻 API 细节），你随时打断问 |
| **就地答疑** | 你卡在某个文件的某几行，我们只聊那几行 |

**建议：第 1、2 站用"我讲"开局**（它们最短但信息密度最高，自己读容易漏掉设计意图），**第 3 站之后改用"你读我考"**，因为那部分自己读得动，而且被考出来的记忆更牢。

# 调研：代码库结构怎么"进上下文"

> 起因：需要一个"带大小/行数/类型标注的目录树概览工具"来解决"结构进不了上下文"的问题吗？
> 这是当前公认的最佳方案吗？
> 结论：**不是，而且它不解决我们实测出来的瓶颈。** 本文记录证据与替代路线。
> 日期：2026-09-28。

---

## 0. 结论先行

1. **目录树概览不是当前公认最佳方案**，也不是业界收敛的做法。它是**低信息密度**的导航辅助，在真实仓库规模（SWE-bench 平均 **438K 行 / 3010 文件**）下不可用。
2. **"结构进不了上下文"这个诊断本身站不住**：我们用现有 `glob` 实测把样例仓库 **39/39 条全列对了**（见 `known_issues.md` 第五节）。当时的真实缺口是**元数据**（符号链接未标注）与**计数推理**，目录树这两样都补不上。
3. **真正的缺口在别处**，且证据非常集中：**没有内容搜索工具**（grep），**没有项目方向性文档加载**（`CLAUDE.md`/`AGENTS.md` 模式）。
4. 因此建议：**不做**目录树工具作为主线；先补 search 工具与方向性文档。目录树若要做，只能是**有界 + 诚实截断**的可选导航辅助。

---

## 1. 行业收敛到了什么

业界对"哪些代码该进上下文"有四条已被命名的路线：

| 路线 | 机制 | 适用 | 代表 |
|---|---|---|---|
| **Agentic search** | 按需 `Glob` / `Grep` / `Read`，由模型自己迭代检索 | **变更频繁、新鲜度优先** | Claude Code、OpenAI 系编码 Agent |
| **仓库地图（repo map）** | tree-sitter 抽符号 → 引用图 → PageRank 排序 → 二分搜索塞进 token 预算 | 大而稳定的库，需要跨文件定位 | Aider |
| 向量语义检索 | 切块 + embedding + 相似度召回 | 自然语言式提问 | Cursor、Windsurf |
| **目录列表 / 文件树** | 列路径（可带大小/类型） | 小仓库的初步导航 | 各类 IDE 插件的文件树面板 |

**行业已明显从"预建索引"转向"按需检索"**：

- **Anthropic 在 2025 年 5 月把 Claude Code 的整条向量检索管线（embedding + 本地向量库 + 切块策略）删掉，换成一个 grep。** Claude Code 作者 Boris Cherny 的原话是它 "outperformed everything, by a lot"，并额外消灭了安全、索引过期、可靠性三类问题。
- Cursor、Windsurf、Cline、Devin、Sourcegraph Amp 随后跟进，纷纷放弃向量索引改用工具驱动检索。
- Anthropic 官方《Effective context engineering for AI agents》(2025-09) 把它形式化为 **just-in-time 加载**：Agent 只持有**轻量标识符**（文件路径、已存查询、链接），运行时用工具动态把数据拉进上下文。

## 2. 实证数据（不是观点）

| 证据 | 数字 |
|---|---|
| SWE-bench 初版基线用 RAG 管线（切块+embedding+top-k） | **1.96%** 解决率 |
| 第一个 Agent 系统 SWE-agent，把检索换成工具（`open_file` / `scroll_down` / `edit_lines`） | **12.47%**（约 6 倍） |
| Amazon AAAI 2026《Keyword Search Is All You Need》 | 纯关键词检索的 Agent 达到 RAG 忠实度的 **>90%**，且**零向量基础设施**；FinanceBench 上 30.40% vs 24.24% |
| DCI（Direct Corpus Interaction，13 个基准） | 多跳 QA **+30.7**、IR 排序 **+21.5**、agentic search **+11** |
| Aider repo map | SWE-bench Lite **26.3%** 解决率、**70.3%** 正确定位到文件；默认地图预算仅 **~1024 tokens** |

> ⚠️ 反方证据也要记：关键词检索是"**超过 90%**"，不是"超过 100%"——索引仍有小幅胜出的空间；向量检索在"自然语言提问 + 海量稳定语料"场景仍更合适。**所以不是"grep 永远赢"，而是"代码这种高度结构化、标识符精确、变更频繁的对象，精确匹配 + 迭代检索更划算"**。

## 3. 为什么"目录树概览"不是答案

1. **信息密度低。** 行业资料直接把 "directory listings, file samples" 归为"在低信噪比内容上浪费 token"的做法——Agent 需要知道**存在哪些函数/类、它们怎么连**，而不是实现细节，更不是文件名的字母序。
2. **不可扩展。** SWE-bench 平均仓库 **438K 行 / 3010 文件**。我们的目标线就是"真实仓库上的真实 issue"，一棵 3000 行的树既塞不进上下文，也无助于定位。
3. **有结构，无语义。** 树告诉你"有哪些文件"，不告诉你"**什么重要、从哪下手**"。真正解决规模问题的是 **repo map**：符号级、按引用图 PageRank 排序、并且**按 token 预算二分拟合**。它是"结构进上下文"的公认最佳形态 —— 而它**不是文件树**。
4. **不解决我们实测的失败。** 那次运行模型已经拿到完整结构（39/39），错在分类计数与符号链接识别。加一棵树不会改变这两点。
5. **已有更轻的等价物。** `glob` 返回的就是带目录标记的完整路径列表，本质就是"扁平化的树"。加大小/行数只是给每个节点补元数据 —— 可以便宜地做在 `read` 的头部，不必新增一个工具。

---

## 4. 那么真正的缺口在哪（对照我们的代码）

| 证据指向的做法 | 我们的现状 | 缺口 |
|---|---|---|
| **内容搜索优先**（grep 是 Claude Code 的核心） | 只有 `read` / `list_dir` / `glob` | ❌ **完全没有搜索工具** ← 最大缺口 |
| 轻量标识符 + JIT 加载 | 路径即标识符，`glob`/`read` 按需取 | ✅ 基本符合 |
| **前置方向性文档**（`CLAUDE.md` / `AGENTS.md` 开局注入） | 无任何项目说明加载 | ❌ **缺失**（Anthropic 明确说 Claude Code 开局先载 `CLAUDE.md`，再用 glob/grep 探索） |
| 元数据信号（目录/文件名/时间作为强线索） | 目录带尾 `/` | ⚠️ 符号链接未标注（模型实测时主动抱怨） |
| 大仓库跨文件定位（repo map） | 无 | ⬜ W6 已规划（AST + 向量 + BM25 + RRF） |
| 运行时探索需要"合适的工具与启发式"，否则会浪费上下文 | 工具集偏薄，且无探索指引 | ⚠️ 见下 |

Anthropic 对"运行时探索"的约束条件说得很直接：*运行时探索比预加载慢，而且 Agent 需要**合适的工具与启发式**；没有它们，Agent 会因工具使用不当、探索低效或遗漏关键信息而浪费上下文。*

## 5. 建议（按性价比排序）

### P0 · 补内容搜索工具 `search`
最高杠杆。支撑"先定位再读"的基本工作流，是 agentic search 的支柱。应支持：正则/字面量、`glob` 过滤、上下文行数、命中数上限 + **诚实截断**（复用本轮建立的口径）。

### P0 · 项目方向性文档加载
在 `intake` 阶段自动载入工作区根部的方向性文件（`AGENTS.md` → `CLAUDE.md` → `README.md`，取首个命中，**按行数/字符数设上限**）。这是"结构进上下文"的**实际最佳实践**：让**项目自己声明**它的结构与约定，而不是让工具去猜。成本极低、收益直接，并且天然适配"产品优先"方向。

### P1 · 元数据补全（不新增工具）
- `glob` 标注符号链接与目录（消除模型的这个抱怨）。
- `read` 头部补上文件大小与行数（已有行数），让模型对"这个文件值不值得读"有判断。

### P2 · 目录树工具（降级为可选导航辅助）
**仅在**上述做完后、且观察到"探索往返次数偏高"时再考虑。若做，硬约束：
- 深度上限 + 条数上限 + **诚实截断**；
- 排序按**相关性**而非字母序（至少让入口文件、包根、测试目录优先）；
- 明确**不作为**主机制 —— 规模问题交给 W6 的 repo map。

### 已规划 · repo map（W6）
若日后要在真实大仓库上做跨文件定位，Aider 式 **tree-sitter 符号 + PageRank + token 预算拟合**才是公认答案。本项目 W6 的"混合检索（AST + 向量 + BM25 + RRF + rerank）"已覆盖其思路，不必另起炉灶。

---

## 6. 对当前方向的影响

"产品优先、评测后置"的目标线是**在一个真实仓库上端到端修好一个真实 issue**。**P0 两项都是这条线的必经之路**：没有 `search` 就无法在几千个文件里定位改动点；没有方向性文档，模型每进一个仓库都要从零摸索。而目录树工具对这条线的贡献有限。

因此：**不实现目录树工具，改为先做 `search` + 方向性文档加载。**

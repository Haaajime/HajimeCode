# Hajime2Code 架构与能力现状

> 用途：把"我们到底实现了什么样的 Agent"讲清楚，并**诚实盘点**能力缺口。
> 对应四个问题：编排层 / 工具调用 / 记忆层 / 技术栈。
> 日期：2026-09-29。凡标 ⚠️/❌ 的都是**尚未实现**，不要让文档替实现说话。

---

## 0. 一句话定位

**基于 LangGraph 手写主图 + LangChain `create_agent` 子图**的编码 Agent 运行时：
工具层可插拔（`@tool` 注册）、事件流可订阅（SSE）、模型可切换（含**零成本的无模型模式**）。

---

## 1. 编排层：我们实现的是"双层图 Agent"

这是本项目最有辨识度的设计，也是面试里的核心叙事。

```
                  intake → plan → act → reflect ─┬─→ act       未过验收，带意见重试
                                                 └─→ finalize → END
                                  │
                                  └── act 内部：create_agent 装配的 ReAct 子图
```

| 层 | 实现 | 管什么 |
|---|---|---|
| **主图** | **手写** `StateGraph`（`graph/builder.py`） | **图级控制流**：规划、验收、回退重试、预算裁剪、后续的并行/审批 |
| **子图** | 官方 `create_agent`（`graph/agents.py`） | **一次 ReAct 执行**：模型调用 → 工具调用 → 重试 |

**职责边界一句话**：主图决定"**下一步做什么**"，子图决定"**这一步怎么做完**"。

**为什么不全用 `create_agent`**：它把图接线藏在内部，无法在节点之间插入"规划 / 反思 / 回退 / 人工审批"。我们要的正是这些控制点。

**状态设计**（`AgentState`，节点只返回**增量**）：

| 通道 | reducer | 用途 |
|---|---|---|
| `messages` | `add_messages`（追加 + 按 id 去重） | 原始对话 |
| `budget` | `add_budget`（**累加**） | steps / llm_calls / tokens / **缓存命中** / 成本 |
| `plan` `todos` `summary` `status` `attempts` `findings` | last-value-wins | 结构化进度 |
| `project_brief` | last-value-wins | 工作区方向性文档（AGENTS.md 等） |

**预算护栏**：`max_steps` / `max_attempts` / token 与成本累计 —— 这是后面所有成本实验的数据来源。

## 2. 工具调用：**完全自动**，靠 function calling

**是自动的** —— 代码里**没有一行硬编码的工具调度逻辑**。链路如下：

1. `@tool` 装饰器把普通函数变成 `StructuredTool`：
   **函数名 → 工具名**，**docstring → 工具描述**，**类型标注 → JSON Schema 参数**
2. `create_agent(model, tools)` 内部对模型 `bind_tools()`；这些 schema 作为 OpenAI
   **`tools` 参数随每一次模型请求发送**
3. 模型返回 `AIMessage.tool_calls`（含工具名与参数 JSON）
4. LangChain 的 `ToolNode` 执行对应工具，把结果作为 `ToolMessage` 追加进消息列表 → 下一轮
5. 循环直到模型不再要求调用工具（或触达递归上限）

**模型实际收到的"说明书"**（本项目导出，`/tmp` 脚本实测）：

| 工具 | 描述（即 docstring 首行） | 参数 | 必填 |
|---|---|---|---|
| `read` | 读取工作区内文本文件，可用 offset/limit 按行截取 | path, offset, limit | path |
| `list_dir` | 列出工作区内某目录的下一层内容（**不递归**） | path | — |
| `glob` | 按 glob 通配符列出路径（支持 `**`），返回 JSON 对象 | pattern, max_results | pattern |
| `search` | 在文件**内容**里按正则搜索（grep），返回 JSON 对象 | pattern, path, file_pattern, ignore_case, context_lines, max_results | pattern |
| `write` | 创建或覆盖文本文件。有副作用 | path, content | — |
| `edit` | 精确字符串替换。old_string 必须唯一 | path, old_string, new_string, replace_all | — |

> **关键认知：docstring 就是 prompt。**
> 我们在这上面花的心思直接决定模型的调用质量。一个实证：模型在真实运行中主动报告
> **"未截断，扫描 24 个文件"** —— 它读到的正是我们在 `search` 的 description 里写的
> "务必检查 `truncated`"。**工具契约写得诚实，模型的行为就诚实。**

## 3. 记忆层：**诚实答案是"基本没实现"**

这是当前**最大的真缺口**，也是面试最容易被问穿的地方。分层盘点：

| 层 | 现状 | 判定 |
|---|---|---|
| **会话内（短期）** | `state.messages` 用 `add_messages` **无界累积**；工具输出有上限（`read` 60K 字符、`glob` 200 条、`search` 50 条），但**消息列表本身没有任何压缩或裁剪** | ⚠️ **缺陷**：长任务必然撑爆上下文 |
| **任务内（工作记忆）** | `plan` / `todos` / `summary` / `budget` 作为结构化通道在节点间传递；`project_brief` 每轮注入 | ✅ 基本可用 |
| **跨任务 / 跨会话（长期）** | **完全没有** | ❌ 空白 |
| **持久化底座** | `build_graph(checkpointer=…)` 参数已接线，但**没有任何地方传入** → 无 checkpoint、无断点续跑、无 time-travel | ❌ W4 |
| **Middleware 机制** | `middleware` 参数已接线到 `create_agent`，但**传的是空元组** → 6 个钩子**一个都没用** | ❌ 机制闲置 |

**所以：说"记忆层实现了"是不诚实的。** 现在只有"原始消息累积 + 几个结构化字段"；
真正构成记忆的要素 —— 压缩、摘要、跨会话召回、语义检索、遗忘与冲突消解 —— **一个都没有**。

### 3.1 面试要的"细致"，具体指什么

按重要性排序，这些是能讲出深度的地方：

1. **上下文压缩**：何时触发、压什么、如何保证不丢关键信息（保真度怎么量）
2. **压缩与缓存前缀的对抗**：压缩省 token，但会破坏 DeepSeek 的前缀缓存 —— **省的钱可能被缓存失效吃回去**（这是 E4 实验的核心，也是本项目最有研究价值的一点）
3. **长期记忆的写入与召回路**：什么时候写、写什么粒度、怎么召回（向量 / 结构化 / 混合 RRF）
4. **选择性遗忘与冲突消解**：新旧信息矛盾时以谁为准
5. **记忆的可观测性**：这轮到底命中了哪几条记忆、对结果有什么影响 —— 否则无法评测
6. **成本**：记忆注入增加每轮前缀 token，必须和缓存命中率一起权衡

### 3.2 建议的实现顺序（M1–M4）

| 阶段 | 内容 | 落在哪 | 为什么这个顺序 |
|---|---|---|---|
| **M1** | **上下文压缩**：接官方 `SummarizationMiddleware` + 按 token 预算裁剪；配套"压缩保真度"指标 | W5 | 不解决它，稍长的任务直接跑不通 —— 是**当下就挡路**的问题 |
| **M2** | **持久化**：`PostgresSaver` → 断点续跑 + time-travel，任务历史可回看 | W4 | 压缩与记忆都需要一个状态底座 |
| **M3** | **长期记忆**：`PostgresStore`（内置向量检索）+ "选取-抽取-合并"写入策略 + 召回可观测 | W6 | 有了底座才谈得上跨会话 |
| **M4** | **记忆评测**：召回命中率、注入前后的成功率与成本变化 | W9 | 把"我实现了记忆"变成"我量化了记忆值多少" |

> 注意 M1 的紧迫性：它不需要数据库、不需要向量库，**现在就能做且立刻有用**。

## 4. 技术栈：**已经是主流选型，"跟进"这件事其实已经做到了**

用户的判断是"大公司都在用 FastAPI + React，我们应该跟进"。实际情况是：

### 已经有了（就是你说的那套）

| 层 | 选型 | 版本 |
|---|---|---|
| 后端框架 | **FastAPI** | 0.141.1 |
| 数据校验 / 配置 | **Pydantic v2** / pydantic-settings | 2.13.5 |
| ASGI | **uvicorn[standard]** | 0.54.0 |
| 流式推送 | **sse-starlette**（SSE） | 3.4.11 |
| 编排 | **LangGraph** / LangChain | 1.2.12 / 1.4.2 |
| 前端 | **React + TypeScript** | 19 / 5.7 |
| 构建 | **Vite** | 6 |
| 样式 | **Tailwind** | 4 |

而且不止于"用了"：我们有 **SSE 实时事件流**（含 `Last-Event-ID` 续传）、
**OpenAPI 自动文档**、**零成本的无模型模式**、**目录选择器**、**前后端版本握手**。

### 尚未落地的（方案里已规划，按需推进）

| 项 | 计划 | 必要性判断 |
|---|---|---|
| Docker 沙箱 bash | W3 | **必需** —— 目标线要求"能跑测试" |
| 权限层（fail-closed + 人工审批） | W3 | **必需** —— 现在 `write`/`edit` 无任何拦截 |
| PostgreSQL（checkpoint + store + 元数据） | W4 | **必需** —— 记忆与续跑的底座 |
| 上下文压缩 | W5 | **必需** —— 见 M1 |
| 混合检索（AST + 向量 + BM25 + RRF + rerank） | W6 | 需要时再上 |
| Qdrant | W6 | 视情况 —— `PostgresStore` 可能已够用 |
| OTel / Arize Phoenix | W5 | 可选 —— 指标自采即能满足实验 |
| 多 Agent 拓扑 | W7 | 可选 |
| MCP 适配器 | — | 可选 |

### 我的判断

**技术栈不需要"跟进"—— 它已经在主流位置上。真正缺的是深度，不是"更 fancy 的组件"。**

现在就把 Qdrant / OTel / 多 Agent 全加上，得到的是**更多组件**，不是**更强的 Agent**。
而**权限、压缩、记忆**是每个真实任务都会用到、且面试必问的能力。

> 这也是项目方案一开始的判断：**"我实现了什么"会持续贬值，"我量化了什么"会持续增值。**
> 跟上技术栈只是入场券；把记忆/权限/评测做出深度才是差异所在。

## 5. 一页速查

**已有**：双层图（手写主图 + 官方子图）· 预算与缓存链路 · 6 个文件工具（含**诚实截断**契约）·
方向性文档注入 · SSE 事件流 + Web 控制台 · 模型/目录选择 · **无模型模式** · 149 条离线测试

**没有**：权限层 · 沙箱执行 · 持久化 · **上下文压缩** · **长期记忆** · 检索 · 多 Agent · 评测

**下一步建议顺序**：
`W3 权限 + 沙箱`（能安全改码/跑测试）→ `M1 上下文压缩`（现在就跑不通长任务）→
`W4/M2 持久化` → `M3 长期记忆` → 再谈检索与多 Agent

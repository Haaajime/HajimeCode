## 1. 方法：什么叫"承重的断言"

注释里最危险的不是写得难看，而是**把机制讲错了** —— 读者（包括未来的自己）会照着学。
但不是每句话都值得验，只挑三类：

| 类型 | 特征 | 例子 |
|---|---|---|
| **因果** | 声称"不做 A 就会 B" | "只把新增部分交回主图，否则会重复累积消息" |
| **库行为** | 声称某个库/框架会怎样 | "LangChain 会把它归一化进 cache_read" |
| **契约** | 声称某条件不满足就会被拒 | "old_string 必须唯一，否则拒绝执行" |

描述性的句子（"这里遍历所有文件"）不值得验，看一眼代码就知道。
**"因为 X 所以 Y"才是需要证据的。**

筛选用 `scripts/audit_claims.py`（只筛不判，判定交给人）。

### 三种核实手法

1. **对照实验**：把代码改成断言的反面，看结果是否真的变差。
   例：把 act 换成不切片版本，比较消息条数。
2. **直接观测**：构造最小场景，把中间数据打出来。
   例：打一条真实响应的 usage_metadata 与 response_metadata。
3. **查测试覆盖**：断言如果是真的，应该有测试能证明它。
   例：查 `test_serve_events.py` 是否覆盖"messages 模式流出非 AIMessageChunk"。

## 2. 案例复盘：一句错了的注释

### 2.1 原状

`graph/nodes/act.py` 里有一段按长度切片的代码，配了这样一句注释：

> 子图基于 add_messages，会把输入消息原样作为前缀回传；只把新增部分交回主图，
> **否则父子图之间会重复累积消息、平白放大 token**。

### 2.2 触发

用户在逐行审阅 `state.py` 的文档时，指出我没讲清 `messages` / `budget` 是做什么的，
只抛出"官方""（追加、按 id 去重）"这类术语。**为了把这句话讲清楚，我必须先搞清
add_messages 的真实行为** —— 于是这句注释的因果就暴露了。

> 这是关键：**批评一处注释，牵出了一处错误。** 想讲清"为什么"，就绕不开"真是这样吗"。

### 2.3 三轮实验

| 实验 | 做法 | 结果 |
|---|---|---|
| 1 | 同一批消息对象经 `add_messages` 二次合并 | **不重复** —— 它给缺 id 的消息补 id 再按 id 合并；内容相同但对象不同的两条则不会误合并 |
| 2 | 把 act 换成不切片版本，跑同一个两轮重试场景 | 消息条数与内容**完全一致**（都 4 条） |
| 3 | 真实 `create_agent` 路径（官方假模型） | 4 条消息、**id 全唯一** |

### 2.4 结论与处置

**那个因果是错的。** 而且切片不只是多余，还隐含一个**位置假设**：
"子图的返回必然以输入为前缀"。一旦子图只返回新增消息，切片会把真实消息**全部切掉**；
全量回传在两种情况下都正确 —— 所以不切片**更安全**，不只是更简洁。

处置：
1. 删掉切片，注释改为说明真实机制，并记录这三轮实验。
2. 补回归测试 `test_retry_does_not_inflate_message_count`（两轮重试后恰好 4 条、id 唯一非空）。
3. **顺手搜了一遍"解释这段代码的文档与注释"**，又改掉 4 处仍在复述旧机制的地方
   （进度表、阅读路线、stub.py 的 docstring、一处断言措辞）。

> 教训：**删代码时要顺手搜"解释这段代码的文字"**，否则文档会继续教一个不存在的行为。

## 3. 本轮审计结果：5 条承重断言

| # | 断言 | 出处 | 核实手法 | 结论 |
|---|---|---|---|---|
| 1 | StaticFiles **每次请求都从磁盘读文件** | `serve/app.py` | 起服务 → 请求 → 直接改盘上的文件 → 再请求（**不重启**）→ 拿到新内容 | ✅ **成立**。这正是"新前端 + 旧后端"错配的成因，也是版本握手的依据 |
| 2 | LangChain **会归一化**缓存字段到 `usage_metadata.input_token_details.cache_read` | `budget.py` | 连续两次相同前缀的真实调用，打印原始元数据 | ✅ **成立，但原表述不够精确**（见下） |
| 3 | `CompiledStateGraph.stream` **无法**写成 Protocol | `serve/runner.py` | 反射看签名 | ✅ **成立**：2 个 `@overload`、15 个参数、11 个仅关键字、带 `**kwargs` |
| 4 | 先注册订阅者再读历史，**否则会丢事件** | `serve/bus.py` | 读源码确认两步是否在同一把锁内 | ✅ **成立**：注册与读历史在同一 `with self._lock`，且 `publish` 用同一把锁 → 相对 publish 原子 |
| 5 | **只有** AIMessageChunk 才是真正的 token 流 | `serve/events.py` | 查测试覆盖 | ✅ **成立**：`test_serve_events.py` 有专门用例（messages 模式流出 HumanMessage 时不得当成模型输出） |

### 3.1 顺带把 budget.py 的说法改精确了

原表述让读者以为 LangChain 映射的是 DeepSeek 的扁平字段。**实测不是**：

第二次调用（缓存命中）的三个字段：
```
usage_metadata.input_token_details.cache_read       512   ← LangChain 归一化的（代码优先读这个）
response_metadata.token_usage.prompt_cache_hit_tokens 512   ← DeepSeek 自己的扁平字段（代码回退读这个）
response_metadata.token_usage.prompt_tokens_details.cached_tokens 512  ← LangChain 实际映射的来源
```

- DeepSeek **同时**给出扁平与嵌套两种形式；
- LangChain 归一化的是**嵌套的** `cached_tokens`；
- 我们优先读归一化字段，回退读扁平字段 —— 两条路实测取到同一个值，回退只是防御。

### 3.2 附带实测出一条对 E4 实验很关键的性质

两次调用的 `input_tokens` **完全相同（都是 674）**，差别只在命中 512 个。
也就是：**缓存只影响成本，不影响 token 数。**

这正是"压缩 ↔ 缓存对抗"实验的立足点 —— 压缩省下的 token，可能同时毁掉前缀缓存，
省下的钱又被吃回去。这条性质现在写在 `budget.py` 的文档里了。

## 4. 为什么这件事值得单独做

- **对项目**：注释里的错误会固化成团队共识。删代码不改文档，等于留了个陷阱。
- **对使用者（正在学 Agent 开发）**：这些注释就是教材。教材错一句，学的人就错一路。
- **对面试**：能讲出"我发现并推翻了自己写的一条注释，因为做了对照实验"，
  比讲"我实现了什么功能"有分量 —— 它证明的是**验证意识**，不是记忆力。
